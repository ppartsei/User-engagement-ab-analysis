# A/B-тестирование нового алгоритма рекомендаций в развлекательном приложении

##  Описание проекта

Данный проект посвящён разработке, проведению и анализу A/B-теста нового алгоритма рекомендаций контента в развлекательном приложении с «бесконечной» лентой коротких видео.

### Контекст бизнеса

Компания разрабатывает развлекательное приложение с бесконечной лентой коротких видео. Основная цель продукта — **удерживать внимание пользователя** как можно дольше.

Монетизация строится на двух моделях доступа к контенту:

1. **Рекламная модель** — бесплатный доступ, доход приносят рекламные ролики, встроенные в ленту.
2. **Подписочная модель** — ежемесячная оплата, которая полностью отключает рекламу и делает просмотр беспрерывным.

Главный двигатель приложения — **алгоритм рекомендаций**, который из миллионов доступных вариантов выбирает те, что с наибольшей вероятностью понравятся конкретному пользователю. Качество работы алгоритма напрямую влияет на выручку компании:

- Если алгоритм работает плохо — пользователь быстро закрывает приложение.
- Если хорошо — пользователь остаётся дольше, что увеличивает выручку.

### Суть эксперимента

До недавнего времени лента формировалась на основе простых эвристик по схеме «популярное за день + новинки». Команда Data Science разработала **новый алгоритм ранжирования контента**, который:

- учитывает персональные интересы пользователя (прошлые отметки «Нравится», длительность просмотра);
- оптимизирован на предсказание вероятности глубокого вовлечения (просмотр более 80% видео).

**Ожидание:** более релевантный контент должен увеличивать время пользователей в приложении.

**Риски:**

1. Пользователи без подписки, максимально поглощённые релевантным контентом, могут начать негативно реагировать на рекламные вставки.
2. Ценность платной подписки «без рекламы» может снизиться, если контент станет слишком поглощающим.

---

##  Цели и задачи проекта

**Основная цель:** провести корректный A/B-тест нового алгоритма рекомендаций и оценить, стоит ли внедрять его в продукт.

### Задачи

1. **EDA исторических данных** — изучение структуры и поведения пользователей до теста.
2. **Расчёт параметров теста** — определение размера выборки и длительности эксперимента.
3. **Мониторинг A/B-теста** — проверка корректности сплитования пользователей.
4. **Анализ результатов** — оценка влияния нового алгоритма на ключевую метрику и формулировка выводов для команды разработки.

В проекте используются три таблицы:

## Ход выполнения проекта

### 1. Работа с историческими данными (EDA)

#### 1.1. Загрузка исторических данных

- Импорт данных из `sessions_project_history.csv` в датафрейм `sessions_history`.

#### 1.2. Знакомство с данными

- Для каждого пользователя рассчитывается количество уникальных сессий.
- Анализируется поведение самого активного пользователя для понимания логики формирования полей.

**Ключевые выводы:**

- `session_number` увеличивается сквозным образом за всё время жизни пользователя (не сбрасывается при пропуске дней).
- Регистрация (`registration_flag`) фиксируется только в день регистрации.

#### 1.3. Анализ числа регистраций

- Агрегация данных по дням: число уникальных пользователей и число зарегистрированных пользователей.
- Построение линейных графиков динамики DAU и регистраций.
- Построение отдельного графика доли зарегистрированных пользователей.

**Ключевые выводы:**

- В августе наблюдался резкий рост DAU (с ~4 000 до ~17 500 пользователей), за которым последовал затяжной спад практически до нуля к 23 сентября.
- Доля зарегистрированных пользователей остаётся критически низкой (4–8.5%) на протяжении всего периода.
- Рост доли в конце периода объясняется тем, что в приложении остались только «ядерные» зарегистрированные пользователи.

#### 1.4. Анализ числа просмотренных страниц

- Анализ первых сессий пользователей.
- Построение столбчатой диаграммы распределения `page_counter`.

**Ключевые выводы:**

- Пик вовлечения — 3 страницы (50 939 сессий) — точка принятия решения пользователем.
- Значительная доля пользователей (41 000+) закрывают приложение после 1–2 видео.
- Количество сессий с 5+ просмотрами резко падает.

#### 1.5. Доля пользователей, просмотревших более четырёх страниц

- Создание столбца `good_session` (1, если ≥4 страниц, иначе 0).
- Построение графика доли успешных первых сессий по дням.

**Ключевые выводы:**

- Доля успешных сессий стабильно держится в диапазоне 29.7–32%.
- Тренд на ухудшение контента отсутствует.

---

### 2. Подготовка к тесту

#### 2.1. Расчёт размера выборки

Параметры:

- Уровень значимости (α): 0.05
- Ошибка второго рода (β): 0.2
- Мощность теста: 0.8
- Базовый уровень доли (p): 0.3
- MDE (относительный): 3% → 0.009 в абсолютных значениях

**Результат:** необходимый размер выборки — **41 041 пользователь на каждую группу** (82 082 всего).

#### 2.2. Расчёт длительности A/B-теста

- Средний дневной трафик: ~9 907 пользователей в день.
- **Расчётная длительность:** 9 дней (округление вверх).

---

### 3. Мониторинг A/B-теста

#### 3.1. Проверка распределения пользователей

- Анализ данных за первый день теста (14.10.2025).
- Группа A: 1 477 пользователей, группа B: 1 466 пользователей.
- Процентная разница: **0.74%** — в пределах нормы (SRM < 1–2%).

#### 3.2. Проверка пересечений пользователей

- Пересечение множеств `user_id` групп A и B: **0 пользователей**.
- Группы абсолютно независимы.

#### 3.3. Равномерность разделения по устройствам

- Построение круговых диаграмм для групп A и B.
- **Вывод:** распределение по устройствам идентично (Android ~44–46%, PC ~25–26%, iPhone ~18–20%, Mac ~10–11%).

#### 3.4. Равномерность распределения по регионам

- Построение горизонтальных столбчатых диаграмм.
- **Вывод:** распределение по регионам сбалансировано (CIS ~43–44%, MENA ~41%, EU ~15%).

#### 3.5. Вывод после проверки A/B-теста

**A/B-тест проходит корректно:**

- Группы сбалансированы по объёму (разница 0.74%).
- Пересечений пользователей нет.
- Распределение по устройствам и регионам равномерное.
- Данные пригодны для дальнейшего анализа.

---

### 4. Проверка результатов A/B-теста

#### 4.1. Получение результатов теста

- Загрузка `sessions_project_test.csv`.
- Создание столбца `good_session` (1, если `page_counter >= 4`).

#### 4.2. Формулировка гипотез

**Нулевая гипотеза (H₀):** Новый алгоритм рекомендаций не влияет на долю успешных первых сессий; конверсия в группе B равна конверсии в группе A.

**Альтернативная гипотеза (H₁):** Новый алгоритм повышает вовлечённость новичков; конверсия в группе B выше, чем в группе A.

**Прокси-метрики:**

- Глубина просмотра среди удержанных пользователей (среднее `page_counter` внутри `good_session`).
- Доля качественных сессий на одного пользователя.

**Барьерные метрики:**

- Конверсия в регистрацию (`registration_flag`).
- Доля «одноразовых» пользователей.

#### 4.3. Сравнение доли успешных сессий

| Группа | Доля успешных первых сессий |
|--------|----------------------------|
| A (контроль) | 31.57% |
| B (тест) | 31.47% |

- **Абсолютная разница:** −0.11 п.п.
- **Относительное изменение:** −0.33%

#### 4.4. Проверка статистической значимости

- **Тест:** `proportions_ztest` (односторонний, `alternative='larger'`).
- **p-value:** 0.5784
- **Уровень значимости:** α = 0.05

**Вывод:** p-value ≫ α. Различие статистически **незначимо**. Нулевая гипотеза не отклоняется.

#### 4.5. Итоговый вывод для команды разработки

**Характеристики эксперимента:**

- Длительность: 20 дней (14.10.2025 — 02.11.2025), что превышает расчётный минимум в 9 дней.
- Объём выборки: 41 041 пользователь на группу (сбалансировано).
- Пересечений нет, распределения по устройствам и регионам равномерны.

**Влияние на ключевую метрику:**

- Новый алгоритм **не улучшил** долю успешных первых сессий (наблюдается даже микро-ухудшение на −0.11 п.п.).

**Статистическая значимость:**

- p-value = 0.5784 ≫ 0.05 → эффект отсутствует, разница — случайный шум.

**Рекомендация:**

- ❌ **Не внедрять** текущую версию алгоритма.
- Вернуться к этапу генерации гипотез и перенастройке модели.
- Проверить барьерные метрики (например, скорость загрузки рекомендаций).
